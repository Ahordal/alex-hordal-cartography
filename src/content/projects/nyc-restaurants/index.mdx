New York City (NYC) is a global hub for diverse cuisine, offering an extensive range of dining experiences that reflect cultures from around the world. With more than 30,000 restaurants currently operating across the five boroughs, a robust food establishment inspection program is essential to maintaining consistent food safety standards and protecting public health.

This project explores restaurant inspection outcomes across New York City through an interactive dashboard that highlights recent inspection results, spatial patterns, and long-term trends, using historical inspection data spanning 2007 to the present.

This project has existed in two versions. The original was built with ArcGIS Dashboards during the [GIS: Cartography and Geovisualization program at NSCC](https://www.nscc.ca/programs-and-courses/programs/plandescr.aspx/geographic-information-systems-gis-cartography-and-geovisualization), hosted on a school-issued ArcGIS Online account. That account no longer exists, and with it the original dashboard, so after graduating I rebuilt the entire project from scratch as a custom-coded web application, giving me full control over the dashboard's data pipeline, design, and long-term hosting.

Rebuilding the dashboard meant replacing every part of the original ArcGIS Dashboards workflow with a codebase I maintain myself. A Node.js pipeline fetches the full [DOHMH New York City Restaurant Inspection Results](https://data.cityofnewyork.us/Health/DOHMH-New-York-City-Restaurant-Inspection-Results/43nn-pn8j/about_data) dataset directly from the NYC Open Data Socrata API in paginated batches, geocodes new or changed restaurant locations through [LocationIQ](https://locationiq.com/), and outputs a static GeoJSON layer with current inspection results for every restaurant in NYC, plus per-restaurant historical inspection files. That pipeline runs automatically every day: a scheduled GitHub Actions workflow handles the daily geocoding backfill and triggers a fresh data fetch and rebuild, and every push to the main branch does the same in between, so the dashboard stays current without any manual data handling.

The frontend is a React and TypeScript application built with Vite, using the ArcGIS Maps SDK for JavaScript to render restaurant locations as a GeoJSON layer rather than relying on ArcGIS Dashboards' built-in widgets. Filtering, search, grade-breakdown charts, and the restaurant detail panel are all custom components wired directly to the map's query and selection state, reproducing the same exploratory interactions as the original dashboard while running as a fully self-hosted, independently deployed web app.

The interactive map allows users to explore restaurant locations and inspection grades, while dynamic dashboard elements update as the map extent changes, supporting analysis at multiple spatial scales. Additional visualizations, including grade distributions, tabular data, and time series charts, provide both aggregate and restaurant-level insights. Users can filter the dataset by grade and borough or select individual restaurants to examine inspection score trends over time.

The workflow involved filtering and organizing the dataset to isolate the most recent inspection results for display on the web map while preserving historical records for temporal analysis. Restaurant locations were displayed as individual points rather than aggregated, preserving important spatial patterns in density and distribution across New York City.

Integrating the web map into the dashboard enabled dynamic, view- and selection-based interactions via linked charts, tables, and filters, allowing users to explore relationships within the dataset in a more exploratory, interactive manner.

<ProjectFigure

The dataset used in this project is derived from restaurant inspection records provided by New York City's Department of Health and Mental Hygiene (DOHMH) and is publicly available on the  <a href="https://data.cityofnewyork.us/Health/DOHMH-New-York-City-Restaurant-Inspection-Results/43nn-pn8j/about_data" target="_blank" rel="noopener noreferrer">NYC Open Data portal</a>.

This dataset was chosen for its strong relevance to public health and daily life, as well as its suitability for spatial analysis. It provides up-to-date restaurant inspection outcomes across New York City, offering insight into the conditions of dining establishments visited by the public. Importantly, it enables analysis of inspection performance over time, highlighting trends in compliance with established health standards.


The DOHMH New York City Restaurant Inspection Results dataset updates daily and covers every sustained or not-yet-adjudicated violation from full and special program inspections conducted within the three years prior to each restaurant's most recent inspection, for restaurants and college cafeterias currently in active status. Each row represents a single violation citation rather than a single restaurant, so an inspection with multiple violations produces multiple rows repeating the same inspection details; restaurants are uniquely identified by their CAMIS record ID. Restaurants with no violations, or that have applied for a permit but haven't yet been inspected (marked with a placeholder inspection date of 1/1/1900), still appear as a single row. As an operational dataset assembled from several administrative systems, it can also contain occasional illogical or missing values.

The pipeline built for this rebuild fetches the dataset directly from the Socrata API and groups its rows by CAMIS to produce two outputs: a single current-state point per restaurant, holding its most recent scored inspection, for the map layer; and a full per-restaurant inspection history for the score-over-time and violation-detail views. Restaurants with no scored inspection yet are excluded from the map, coordinates that fall outside a rough NYC bounding box are treated as invalid and reverted to DOHMH's own coordinates, and restaurant and address text is normalized to build the dashboard's search index.

While the restaurant counts vary significantly by borough, the trend does not appear to be correlated to population alone. For example, the estimated population of Manhattan in 2020 was 1,694,251—the second-lowest among the 5 boroughs (New York City Department of City Planning, 2024)—yet it accounted for 57.6% of NYC's total tourism jobs (Office of the New York State Comptroller, 2021). This suggests that restaurant density is likely influenced by tourism and commercial activity, which increases demand for dining establishments beyond what the resident population alone would indicate.

The same pattern carries through the grade breakdown: boroughs with higher
restaurant density, particularly Manhattan, also show higher counts across
every inspection grade. This reflects overall restaurant volume rather
than a performance difference, since higher density increases total
inspection counts without indicating a decline in sanitary conditions.

<PageSubsection
  title="Temporal Trends"
  class="subsection-wide"
>
A review of restaurant inspection histories using the Restaurant
Performance chart reveals that performance is dynamic. While some
establishments maintain relatively consistent scores across multiple
inspections, others show noticeable fluctuations, with scores improving or

  title="Interaction Insights"
  class="subsection-wide"
>
The dashboard's interactive map directly shapes how the dataset reads: the
stats panel, grade breakdown chart, and restaurant list all update
dynamically to match the current map extent. As users pan and zoom across
the city, the subset of data being visualized changes, revealing patterns
that aren't apparent at a city-wide view.

This relationship between map extent and the rest of the dashboard means
interpretation varies with scale: broader views highlight citywide trends,
while more focused views reveal finer spatial variation. The Grade and
Borough filters, search field, and Search Radius tool narrow that same
view further, letting users isolate specific subsets of the data without
leaving the map.

<PageSubsection
  title="Data & Dashboard Limitations"
  class="subsection-wide"
>
The following limitations were identified during the development and use of the
dashboard:

          <ul class="list-justified">
            <li>Multiple restaurants at the same or adjacent address often plot at the same map point, so a single click can only resolve to one restaurant even when several share it. The Stats Panel and Grade Breakdown chart aren't affected by this, since both tally every restaurant currently in view from the underlying data rather than from what's visually rendered as separate dots; the Restaurant List panel is the reliable way to browse and select between restaurants sharing a point.</li>
            <li>The dashboard has no backend or live database: restaurant data ships as one static GeoJSON file (all ~30,600 restaurants, about 32MB, loaded up front) plus over 27,000 small per-restaurant history files fetched on demand and capped at 50 entries in an in-memory cache. Static files keep hosting free and the app simple to reason about, since every filter, search, and sort runs entirely in the browser against data already downloaded, but a live database would scale further past this dataset's size, at the cost of hosting fees and operational complexity a personal project doesn't need.</li>
            <li>Data is only as fresh as the last build. DOHMH inspections are refetched dataset-wide at most once a day, driven by the scheduled geocoding backfill and any push to the main branch, not a live feed, so a newly published inspection can take up to a day to appear.</li>
            <li>LocationIQ's free tier caps geocoding at about 4,900 lookups a day. A cold cache would take roughly a week to fully resolve; day to day this only matters for new or changed restaurants, since the daily backfill skips everything already cached.</li>
          </ul>
